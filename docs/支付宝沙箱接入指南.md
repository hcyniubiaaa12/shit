# 支付宝沙箱接入指南

> 面向：Mall-X 支付模块（`mall-pay-service`）
> 目标：**不用真钱**、用支付宝官方沙箱完成"下单 → 收款 → 回调入账 → 退款"全链路演示。

## 1. 设计要点（答辩重点）

支付模块用**渠道抽象**把"谁证明钱到账"隔离出来，业务链路完全复用：

```
PayService（幂等三件套 + 金额核对 + 订单/余额同步）
      │
      ▼
AlipayGatewayClient（接口）
      ├── AlipaySandboxClient   ← 真实沙箱：页面支付 + RSA2 验签 + 渠道退款
      └── MockAlipayClient      ← 本地演示：无密钥也能跑通全流程
```

| 能力 | 沙箱 | Mock |
|---|---|---|
| 创建支付 | 返回支付宝收银台 URL | 返回本系统演示支付页 |
| 到账证明 | 支付宝异步通知 + **RSA2 验签** | `/api/pay/mock/callback` |
| 退款 | `alipay.trade.refund`（`out_request_no` 幂等） | 同步成功 |
| 关单 | `alipay.trade.close` | 仅打日志 |

切换方式：`mall.alipay.enabled`（`false`=Mock，`true`=沙箱）。

**回调幂等与安全**（`PayService.handleAlipayNotify`，顺序不可调换）：

1. **RSA2 验签** —— 证明通知确实来自支付宝，防伪造回调；验签失败直接拒绝
2. **交易状态校验** —— 仅 `TRADE_SUCCESS` / `TRADE_FINISHED` 才入账
3. **Redisson 分布式锁** `pay:notify:{payNo}` —— 并发回调只进一个
4. **状态机条件更新** `UPDATE pay_info SET status=1 WHERE id=? AND status=0` —— 重复回调 0 行即幂等返回
5. **金额核对** 渠道实付必须等于支付单金额，不一致拒绝入账
6. **唯一索引兜底** `pay_info.uk_out_trade_no`

## 2. 获取沙箱密钥

1. 登录 [支付宝开放平台](https://open.alipay.com/)→ 控制台 → **沙箱**（或直接访问 <https://open.alipay.com/develop/sandbox/app>）
2. 在「沙箱应用」页记下 **APPID** 和 **支付宝网关**（`https://openapi-sandbox.dl.alipaydev.com/gateway.do`）
3. 用[支付宝密钥生成工具](https://opendocs.alipay.com/common/02kipl)生成 **RSA2** 密钥对：
   - 工具产出的 **应用私钥** → 填到 `private-key`
   - 把工具产出的 **应用公钥** 填进沙箱控制台「接口加签方式」→ 保存后控制台会显示 **支付宝公钥** → 填到 `alipay-public-key`

> 私钥 = 你的，用来给请求签名；支付宝公钥 = 支付宝的，用来验支付宝的回调签名。两者不能混。

### 2.1 证书模式（控制台对资金类接口的要求）

退款等**资金支出类接口**要求"公钥证书"模式。在控制台「接口加签方式 → 公钥证书」用密钥生成工具产出
**CSR** 上传后，控制台签发三张证书，放到项目根 `certs/` 目录：

| 文件 | 作用 |
|---|---|
| `appPublicCert.crt` | **应用公钥证书**：你的应用公钥在里面，支付宝用它验你的请求签名 |
| `alipayPublicCert.crt` | 支付宝公钥证书：回调验签用（证书模式下**不再需要** `alipay-public-key` 文本） |
| `alipayRootCert.crt` | 支付宝根证书：校验上面两张的合法性 |

> ⚠️ 这三张证书是**由某一把应用私钥对应的 CSR 签发的**，必须与 `private-key` 是**同一对密钥**。
> 换模式/重新生成密钥后仍粘着旧私钥，是 `invalid-signature` 的高频原因。
>
> 好消息：这一项现在**在启动期就会被本地拦下**并打印双方指纹（`AlipayKeyInspector` 预检）：
>
> ```
> [ALIPAY] 预检通过: 应用私钥 ↔ 应用公钥证书配对一致（证书主体 CN=...-APPID,OU=Alipay,...）
> ```
>
> 不配对时会直接启动失败并提示重新生成密钥对，不会再让你到收银台白页才发现。
> 公钥模式下想手工核对"应用私钥 ↔ 控制台应用公钥"，可跑 `scripts/check-alipay-keypair.ps1`；
> 启动日志里也会打印本私钥对应的**应用公钥**（`[ALIPAY] 预检: 本私钥对应的应用公钥...`）供逐字比对。

## 3. 配置（密钥不要提交仓库）

推荐用**本地覆盖文件**（已在 `.gitignore` 忽略）。证书模式（推荐）：

```yaml
# mall-backend/mall-pay-service/src/main/resources/application-local.yml
mall:
  alipay:
    enabled: true
    app-id: "9021000150666839"
    sign-mode: "cert"                 # cert=证书模式（推荐）；publicKey=公钥模式
    app-cert-path: "C:/.../certs/appPublicCert.crt"
    alipay-public-cert-path: "C:/.../certs/alipayPublicCert.crt"
    alipay-root-cert-path: "C:/.../certs/alipayRootCert.crt"
    private-key: "MIIEvQIBADANBgkq...（必须与上面三张证书同一对密钥）"
    return-url: "http://localhost:5173/pay/result"
    # 关键：必须是支付宝服务器能访问到的地址，见第 4 节
    notify-base: "https://你的公网地址"
```

公钥模式（`sign-mode: "publicKey"`）则用 `private-key` + `alipay-public-key` 两个值，不需要证书：

```yaml
    sign-mode: "publicKey"
    private-key: "MIIEvQIBADANBgkq..."        # 工具产出的应用私钥
    alipay-public-key: "MIIBIjANBgkqhkiG..."  # 控制台显示的支付宝公钥（不是应用公钥！）
```

**密钥格式**：工具导出的是 PEM（多行 + `-----BEGIN-----` 头尾），代码已做归一化，
**PEM 和单行 Base64 两种写法都可以直接粘贴**，不必手工去头尾/删换行。
（`AlipaySandboxClient.normalizeKey` 会剥掉头尾与所有空白字符后交给 SDK；
该行为有回归测试 `verifyNotify_pemFormattedKeys_areNormalizedAndPass` 保护。）

启动时带上 profile：

```bash
java -Dspring.cloud.nacos.discovery.ip=172.16.74.34 \
     -Dspring.profiles.active=local \
     -jar mall-pay-service/target/mall-pay-service-0.1.0-SNAPSHOT.jar
```

或者用环境变量（更适合 CI/容器）：

| 环境变量 | 说明 |
|---|---|
| `MALL_ALIPAY_ENABLED` | `true` 启用沙箱 |
| `MALL_ALIPAY_APP_ID` | 沙箱 APPID |
| `MALL_ALIPAY_PRIVATE_KEY` | 应用私钥 |
| `MALL_ALIPAY_PUBLIC_KEY` | 支付宝公钥 |
| `MALL_ALIPAY_NOTIFY_BASE` | 异步通知公网基地址 |
| `MALL_ALIPAY_GATEWAY` | 网关地址（生产改为 `https://openapi.alipay.com/gateway.do`） |

**行为约定**：`enabled=true` 但密钥/证书没配齐（公钥模式缺 `alipay-public-key`，证书模式缺任一证书）时，
pay-service **启动直接失败**并给出明确报错；证书模式还会额外校验"应用私钥 ↔ 应用公钥证书"是否配对。
这是刻意的——宁可启动报错，也不要出现"以为在收真钱、其实用的 Mock"，或者"跳到收银台才告诉你验签失败"。

## 4. 关键前提：异步通知必须公网可达

支付宝要主动 POST 通知你的服务器，**`localhost` 收不到**。两种做法：

| 方式 | 做法 | 适用 |
|---|---|---|
| 内网穿透（推荐演示用） | 用 ngrok / cpolar / frp 把网关 `8090` 暴露，把公网地址填 `notify-base` | 本机演示 |
| 部署到公网服务器 | 直接把 `notify-base` 设为域名 | 真实上线 |

实际通知地址 = `{notify-base}/api/pay/alipay/notify`。

> 网关白名单已放行 `/api/pay/alipay/notify`（支付宝不会带 JWT），
> 安全性由 pay-service 的**验签 + 金额核对**保证，不靠鉴权。

## 5. 演示流程

1. 用 `user1 / 123456` 登录商城，下单 → 进入支付页
2. 支付页检测到 `realChannel=true`，显示「**前往支付宝付款**」
3. 点击后新窗口打开支付宝收银台 → 用**沙箱买家账号**登录并付款
   （沙箱买家账号/密码在沙箱控制台「沙箱账号」页；余额可在那里充值）
4. 付款后支付宝：
   - **异步通知** `{notify-base}/api/pay/alipay/notify` → 后端验签、核额、入账、订单 0→1、商家余额 +
   - **同步跳转** `return-url` → 前端 `/pay/result` 轮询确认真实入账状态
5. 支付页轮询到已支付 → 自动跳转订单列表
6. 退款：订单列表发起退款 → pay-service 调 `alipay.trade.refund` → 订单 1→6、商家余额 −

> **本机没有公网地址也能跑通**：支付页和 `/pay/result` 轮询的是
> `POST /api/pay/sync/{orderNo}`（**主动查单补偿**），后端会拿 `alipay.trade.query`
> 找支付宝确认真实收款结果，确认已付款就走与异步通知**完全相同**的幂等入账链路。
> 即"异步通知为主、主动查单为辅"：通知到不了（或丢了、延迟了）也不会让订单卡在待支付。
> 接口内部有节流（同一支付单数秒只查一次渠道），前端 1s 轮询不会打爆支付宝。

> 同步跳转**不代表已入账**（用户可能直接关页面），所以 `/pay/result` 页设计成轮询后端状态，
> 而不是根据 URL 参数判成功——这是常见坑。

## 6. 联调排错

| 现象 | 原因 / 处理 |
|---|---|
| 启动报"密钥未配置齐全" | `enabled=true` 但 appId/privateKey（+ 公钥或三个证书）有缺失 |
| 启动报"应用私钥与应用公钥证书不是同一对密钥" | 证书模式下粘了别的密钥对的私钥（换模式/重新生成密钥后最常见）。到控制台重新生成密钥对并下载三个证书，或把与该证书配对的私钥填回 `private-key`；报错里已打印双方模数指纹 |
| 启动报"应用私钥不是合法 RSA/PKCS8" | 私钥复制不完整，或末尾混入了引号/全角标点；重新整段复制 |
| 启动日志警告"notify-url 指向本机" | `notify-base` 是本机地址，支付宝访问不到：付款能成功，但订单不会自动变已支付（见第 4 节） |
| 支付页只显示"模拟支付"按钮 | 仍是 Mock 渠道：检查 `enabled`、是否带了 `-Dspring.profiles.active=local` |
| **跳转支付宝后白页报 `invalid-signature`，且"网关生成的验签字符串"里没有 `biz_content`** | 已修复：跳转地址取错了。必须用 `pageExecute(req, "GET")` 拿**完整 URL**；默认 `pageExecute(req)` 返回的是 POST 表单，其 `action` 只带协议参数（`biz_content` 在隐藏域里），而 `sign` 是按"含 biz_content"算的 → 必然验签失败。见 §6.1 |
| 跳转支付宝后报 `invalid-signature`，但验签串里**有** `biz_content` | 签名密钥与控制台登记的公钥不配对：证书模式看 `appPublicCert.crt` 与 `private-key` 是否为同一对（启动预检会拦）；公钥模式看控制台「应用公钥」是否等于启动日志里打印的那串 |
| 跳转支付宝后报 `invalid-app-id` | APPID 与网关不匹配（沙箱 APPID 必须配沙箱网关） |
| 付款成功但订单一直"待支付" | ①**主动查单已兜底**：支付页/落地页会自动向支付宝查单确认，正常几秒内入账；②若仍不入账，看 pay-service 日志的 `[ALIPAY] 主动查单` 结果：`exists=false` 说明沙箱账号其实没付成功；③异步通知本身需要公网 `notify-base`（本机开发收不到属正常，靠查单兜底） |
| 订单已取消，但用户仍付款成功 | **悬挂款**：订单取消只关了本地 `pay_info`，渠道交易当时可能还没关。三层防护：①创建支付带 `timeout_express=30m`，与订单超时同步到期；②**定时关单补偿** `PayCloseSweeper`（默认每 60s 扫最近 6 小时关闭的支付单：渠道没付就调 `alipay.trade.close` 关掉交易，付了就原路退回）；③前端轮询 `/api/pay/sync` 时也会即时对账。退款记录可在管理后台退款列表看到，落地页提示"订单已取消，款项已退回" |
| 想让取消订单**立刻**关掉渠道交易 | 调 `POST /api/pay/close/{orderNo}`（幂等，订单号或支付单号均可）。定时补偿是兜底，这是"当场关掉"的入口，供 order-service 编排或运维手工调用 |
| 落地页一直"尚未确认到账" | 支付宝同步跳转回传的是**支付单号**（`out_trade_no`），不是订单号。后端 `PayService#findForSync` 已兼容两者；创建支付时也会把自己的 `orderNo` 挂在 `return-url` 上带回来 |
| 回调日志出现"验签失败" | 公钥模式：`alipay-public-key` 填错（填成了应用公钥）；证书模式：`alipay-public-cert-path` 指错文件。或参数被加工过（必须用原始 Map 验签） |
| 回调"金额不一致，拒绝入账" | 订单金额与实付不符（如测试时手工改过金额） |
| 退款报 `ACQ.SYSTEM_ERROR` | 沙箱账户余额不足，或该笔交易不支持退款 |
| 重复回调会不会重复入账 | 不会：锁 + `WHERE status=0` 条件更新 + 唯一索引三层兜底 |

### 6.1 为什么"跳转地址"必须自己拼对（本轮踩坑记录）

`alipay.trade.page.pay` 有两种取跳转地址的方式，差别是致命的：

| 调用 | 返回 | 能不能直接 `window.open` |
|---|---|---|
| `pageExecute(req)`（默认） | **HTML 表单**，给浏览器 POST 用 | ❌ 只取 `action` 会少 `biz_content` |
| `pageExecute(req, "GET")` | **就是一条完整 URL**（含 `biz_content`） | ✅ 直接打开 |

实测证据（POST 表单的 `action` 参数集）：

```
charset, method, sign, return_url, notify_url, version, app_id, sign_type, timestamp, alipay_sdk, format
```

—— 该有的协议参数都在，**唯独没有 `biz_content`**，而 `sign` 是按"含 `biz_content`"算出来的。
浏览器 GET 这个地址后，支付宝重算待签串（回显里也恰好只少 `biz_content`）→ 与实际签名不一致 →
`invalid-signature(40002)`。项目里曾把这条 748 字符的 URL 存成 `logs/probe-url.txt`，
是这次定位的关键物证。

代码位置：`AlipaySandboxClient#buildGatewayUrl`（并有一道硬校验：URL 里没有 `biz_content` 直接抛错，
防止该缺陷回归）；回归测试 `createPay_payUrlContainsBizContentAndSelfConsistentSignature`
会重算签名确认"这条 URL 支付宝能验通"。

> 顺带纠正一个历史误判：早期记录里写过"沙箱公钥模式会被拒（invalid-signature）"，
> 其实与加签模式无关，就是上面这个 `biz_content` 缺失。两种模式现在都验证可用。


## 7. 生产环境差异

| 项 | 沙箱 | 生产 |
|---|---|---|
| 网关 | `openapi-sandbox.dl.alipaydev.com` | `openapi.alipay.com` |
| 密钥 | 沙箱密钥 | 正式应用密钥（需企业实名） |
| 买家 | 沙箱买家账号 | 真实支付宝 |
| 异步通知 | 同样需要公网地址 | 需 HTTPS + 备案域名 |

代码无需改动，只改配置。

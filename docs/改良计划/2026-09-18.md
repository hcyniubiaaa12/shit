> 承接《改良计划.md》（2026-09-06）与 2026-09-13 迭代记录第六节遗留事项
> 「支付宝沙箱密钥待配置」——本轮将支付渠道从 Mock 演示升级为支付宝沙箱真实接入。
> 分支：`feat/alipay-sandbox-pay`（PR 合入 `main`，不直接推 main）。

## 一、背景

原支付模块只有 Mock 渠道：支付页展示「模拟支付成功 / 模拟支付失败」按钮，
由 `/api/pay/mock/callback` 触发入账。`AlipayGatewayClient` 接口注释里标着
`AlipaySandboxClient（TODO：接入支付宝开放平台沙箱）`，即渠道抽象已就位但真实实现缺失。
本轮补齐真实实现，并保持 Mock 可用（本地无密钥也能跑通全流程）。

## 二、渠道抽象重构

| 项 | 改动 |
|---|---|
| 返回值 | `createPay` 由返回 `String`（payNo）改为返回 `PayCreateResult`（payNo / orderNo / 应付金额 / **支付跳转 URL** / 是否真实渠道） |
| 退款 | `refundPay` 增加 `reason` 参数；失败改为 **抛 `BizException`**，不再依赖 `MOCK-REFUND-` 字符串前缀判断成功 |
| 新增能力 | `closePay` 关单（订单取消后防止继续付款）、`channelCode()`、`isRealChannel()` |
| 新增方法 | `PayInfoMapper.markClosed`（`WHERE status = 0` 条件更新，关闭支付单） |

## 三、真实沙箱实现

新增 `AlipaySandboxClient`（`com.alipay.sdk:alipay-sdk-java:4.38.200.ALL`，父 pom 统一管版本）：

| 能力 | 支付宝接口 |
|---|---|
| 电脑网站支付 | `alipay.trade.page.pay` —— 生成收银台跳转 URL（从返回表单的 `action` 提取） |
| 退款 | `alipay.trade.refund` —— `out_request_no` 作渠道侧幂等号 |
| 关单 | `alipay.trade.close` —— 失败不阻断业务，仅告警日志 |
| 回调验签 | `AlipaySignature.rsaCheckV1`（RSA2） |

装配策略（`GatewayConfiguration`，沙箱与 Mock **互斥**）：

| `mall.alipay.enabled` | 三密钥 | 结果 |
|---|---|---|
| `false`（默认） | 任意 | `MockAlipayClient`，本地演示闭环 |
| `true` | 齐全 | `AlipaySandboxClient`，真实沙箱收款 |
| `true` | 缺失 | **启动直接失败**（`IllegalStateException`，报错指明缺哪个变量） |

> 最后一条是刻意设计：宁可启动报错，也不要出现「以为在收真钱、其实用的 Mock」。

## 四、回调安全（本轮重点）

`POST /api/pay/alipay/notify` 处理顺序**不可调换**：

1. **RSA2 验签** —— 证明通知确实来自支付宝，防伪造回调
2. **交易状态校验** —— 仅 `TRADE_SUCCESS` / `TRADE_FINISHED` 才入账
3. **Redisson 分布式锁** `pay:notify:{payNo}` —— 并发回调只进一个
4. **金额核对** —— 渠道实付必须等于支付单金额，不一致拒绝入账
5. **状态机条件更新** —— `UPDATE pay_info SET status=1 WHERE id=? AND status=0`，重复回调 0 行即幂等返回
6. **唯一索引兜底** —— `pay_info.uk_out_trade_no`

任何一步不通过均返回纯文本 `failure`（应答体不能包成统一 JSON，否则支付宝会一直重试）。

**网关白名单**：`/api/pay/alipay/notify` 加入 `AuthGlobalFilter.GUEST_PATHS` ——
支付宝服务器没有也不可能有 JWT，安全性由下游验签 + 金额核对保证，不靠鉴权。

## 九、当日追加修复：跳转收银台报 `invalid-signature` 的两个根因

> 上一节交付后开始联调真实沙箱，点「前往支付宝付款」跳到收银台后**白页报**
> `错误代码 invalid-signature 错误原因：验签出错…`。本节记录定位过程与修复。

### 9.1 根因一（真正的元凶）：跳转地址取错，丢了 `biz_content`

`alipay.trade.page.pay` 取跳转地址有两种调用，差别致命：

| 调用 | 返回 | 能否直接 `window.open` |
|---|---|---|
| `pageExecute(req)`（默认，原实现用的） | **HTML 表单**（给浏览器 POST 用） | ❌ 只取 `action` 会少 `biz_content` |
| `pageExecute(req, "GET")`（修复后） | **一条完整 URL**（含 `biz_content`） | ✅ |

原来的 `buildGatewayUrl` 用正则从表单里抠 `action` 当跳转地址。实测该 `action` 的参数集是：

```
charset, method, sign, return_url, notify_url, version, app_id, sign_type, timestamp, alipay_sdk, format
```

协议参数一个不少，**唯独没有 `biz_content`**（它在表单隐藏域里），而 `sign` 是按"含 `biz_content`"算的。
浏览器 GET 这条地址 → 支付宝重算待签串（错误回显里也恰好只少 `biz_content`）→ 与实际签名不一致 →
`invalid-signature(40002)`。

**两条独立物证**：
1. 支付宝错误页回显的"网关生成的验签字符串"里恰好缺 `biz_content`；
2. 上一轮调试留在 `logs/probe-url.txt` 的**运行时真实 URL 只有 748 字符且不含 `biz_content`**，
   与探针里 POST 表单的 `action` 完全对应。

### 9.2 根因二：证书模式下回调验签公钥为空

`verifyNotify` 固定用 `AlipaySignature.rsaCheckV1(params, alipayPublicKey, …)`，
但证书模式的 `application-local.yml` 里**没有 `alipay-public-key`**（控制台切证书模式后也不再提供），
等于拿 `null` 验签 → **每一条真实异步通知都会失败**，订单永远停在"待支付"。
修复：证书模式改用 `AlipaySignature.rsaCertCheckV1(params, alipayPublicCertPath, …)`，
验签公钥取自支付宝公钥证书。

### 9.3 加固：启动预检（把"跳转才发现"的错误提前到启动期）

新增 `AlipayKeyInspector`（`com.mall.pay.config`，本地判定，不依赖网络），
在 `AlipaySandboxClient` 构造时执行：

| 检查 | 行为 |
|---|---|
| 应用私钥能否解析成 RSA/PKCS8 | 失败即启动失败（复制坏一个字符、混入全角引号等） |
| **证书模式**：应用私钥 ↔ `appPublicCert.crt` 是否同一对密钥 | 不配对即启动失败，并打印**双方模数指纹**（本轮真正耗时最久的就是这个：换证书模式后仍粘着旧私钥） |
| **证书模式**：`alipayPublicCert.crt` 可解析 | 失败即启动失败（否则回调必然验签失败） |
| **公钥模式**：打印本私钥对应的「应用公钥」 | 便于与控制台登记值逐字比对 |
| `notify-url` 是否指向本机 | 打 WARN：付款可成功，但订单不会自动变已支付 |

`buildGatewayUrl` 另加一道硬闸门：生成的 URL 里**没有 `biz_content` 直接抛错**，防止缺陷回归。

## 十、当日追加：把支付闭环补完（通知到不了也能确认收款）

> 第九节修完跳转后，用沙箱买家账号真实付了一笔：**支付宝侧成功，本系统订单却停在待支付**。
> 排查后发现不是"通知没配好"这么简单，而是支付模块缺了三块能力，本次补齐。

### 10.1 现场证据

| 检查 | 结果 |
|---|---|
| 支付宝查单（`alipay.trade.query`） | `P2609181351305277` → `TRADE_SUCCESS`，实付 39.00，渠道流水 `2026091822001469660509334729` |
| 本地库 | 同号支付单 `status=3`（已关闭）、`notify_time=NULL`；订单 `26091813513026167` `status=4`（**已取消**） |

也就是说：这笔钱**付成功了，但订单在下单 30 分钟后已被取消**，而支付宝侧交易当时并没有被关掉。

### 10.2 三个缺口与修复

| # | 缺口 | 后果 | 修复 |
|---|---|---|---|
| 1 | 入账**只依赖异步通知**，而 `notify-base=localhost` 支付宝访问不到 | 钱付了、订单永远待支付 | 新增**主动查单补偿** `POST /api/pay/sync/{orderNo}`（`PayService#syncPayStatus`）：前端支付页/落地页轮询它，后端调 `alipay.trade.query` 确认真实收款 → 走与通知**完全相同**的幂等入账链路（锁 + `status=0` 条件更新 + 唯一索引）。Redis `SETNX+TTL` 节流（同一支付单 3 秒一次），Redis 挂掉则放行（宁可多查不能看不到结果） |
| 2 | 落地页把支付宝回传的 `out_trade_no`（=**支付单号**）当订单号查状态 | 永远查不到 → 一直"尚未确认到账" | `PayService#findForSync` 兼容"订单号/支付单号"；创建支付时把自己的 `orderNo` 挂在 `return-url` 上带回来（`AlipaySandboxClient#returnUrlWithOrderNo`），落地页优先用它 |
| 3 | 订单取消只直写本地 `pay_info`（单库演示约定），**从未调用 `alipay.trade.close`** | 订单已取消、用户手里收银台页面还开着 → 照样能付款成功 → **悬挂款**：既不能入账（订单没了）也不会退（**实测就是这个场景：用户手动取消订单后仍付款成功**） | ①**预防**：创建支付带 `timeout_express=30m`（与订单超时对齐，过期收银台不可支付）；②**同步关单**：新增 `POST /api/pay/close/{orderNo}`，`PayService#closePay` 两种情形都处理（待支付→关渠道+置关闭；已关闭→对账）；③**定时关单补偿** `PayCloseSweeper`（`@Scheduled`，默认 60s，可配 `mall.pay.close-sweep-interval-ms`）：扫最近 6 小时关闭的单，渠道没付就关掉交易、付了就原路退回；④**兜底**：`syncPayStatus` 查到"已关闭却已收款"也会自动退回 |

入账/退款前的**金额核对**是硬门槛：渠道实付与支付单不一致时，既不入账也不退款，只记 ERROR 等人工介入。

> 为什么关单补偿放在 pay-service 而不是让 order-service 直接调：项目里目前**没有**任何
> Feign / RestTemplate / WebClient（服务间调用尚未搭建），而 order-service 的取消链路是"单库直写"约定。
> 定时补偿不需要跨服务改动就能把渠道交易收口；正解（取消时同步调 `/api/pay/close/{orderNo}`）
> 留作遗留项，两条路互不冲突。

### 10.4 仍然遗留（下次迭代）

- **取消订单时同步关渠道交易**：正解是 order-service 取消链路编排
  "关本地支付单 + 调 `POST /api/pay/close/{orderNo}`"（Feign 或 MQ 事件，
  项目目前两者都未搭建）。现阶段由 `timeout_express` + 定时关单补偿 + 悬挂款自动退款等效兜底。
